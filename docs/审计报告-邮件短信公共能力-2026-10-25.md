> 审计对象：`G:\Code\Rust\Pek.RMail`（crate `pek-rmail` v0.1.0）、`G:\Code\Rust\Pek.RSms`（crate `pek-rsms` v0.1.0）

> 公共库：`G:\Code\Rust\DH.RustBase`（crate `dhrust` v0.2.0）

> **实施状态（2026-10-25）**：P0 已落地（提交 `6956aa1`）——新增 `config::TomlConfigStore<T>`；`Pek.RMail`/`Pek.RSms` 已切换并完成凭据 `Debug` 脱敏。P1/P2 待办。

## 1. 结论摘要

两个库当前质量基线良好：

- `cargo clippy --all-targets`：**零告警**；
- Pek.RMail：10 项端到端 + 4 项文档测试全绿；
- Pek.RSms：2 项签名黄金样本 + 14 项端到端 + 2 项文档测试全绿；单服务商特性裁剪零告警；
- 两者 `x86_64-unknown-linux-musl` 交叉编译通过；
- 生产代码几乎无 `unwrap/expect/panic/unsafe`（仅 `ContentType::parse` 固定 MIME 一处 `expect`）。

主要问题不在“能不能跑”，而在**重复实现与少量边界/资源风险**：

| 优先级 | 问题 | 影响面 |
|---|---|---|
| **P0** | `Mailer`/`Smser` 与 `MailSettingsFile`/`SmsSettingsFile` 的配置生命周期代码高度重复 | 两项目 ~200 行可合并 |
| **P0** | `MailData.password` / `SmsData.access_secret` 通过 `#[derive(Debug)]` 可直接打印 | 凭据泄露风险 |
| **P1** | SMTP 附件整文件读入内存；邮件队列无上限 | 大附件/突发流量 OOM |
| **P1** | SMS `SmsData::extend_map` 每次调用都重新解析 JSON，单次发送解析 5~10 次 | 无效 CPU/分配 |
| **P1** | SMS HTTP 重试只覆盖传输错误，不覆盖 5xx/429 | 与 C# `Retry` 语义有差异 |
| **P2** | 表单编码、JSON 容错取值、UTC 时间格式、手机号拆分/占位符替换等小工具重复 | 可下沉 dhrust |
| **P3** | `AccountFailure`/`AllFailed`、后台线程包装等结构相似 | 可选统一 |

## 4. 推荐下沉到 DH.RustBase 的候选

### 4.1 P0：`dhrust::config::TomlConfigStore<T>`

**目标**：消除 `MailSettingsFile`/`SmsSettingsFile` 与 `Mailer`/`Smser` 的配置生命周期重复。

**现状重复**：

- 文件字段：`Option<Mutex<XxxSettingsFile>>` + `Arc<RwLock<XxxSettings>>`；
- 方法：`open/open_in/with_settings/config_path/settings/take_notes/reload_if_changed/save_settings/replace_settings`；
- 锁毒化处理：`unwrap_or_else(|poisoned| poisoned.into_inner())` 重复 8 处以上；
- 保存：`settings.clone()` → `settings_mut` → `save()` → 更新共享快照。

**建议 API**：

```rust
pub struct TomlConfigStore<T> {
    // 内部：Option<Mutex<TomlConfig<T>>> + Arc<RwLock<T>>
}

impl<T: Serialize + DeserializeOwned + Default> TomlConfigStore<T> {
    pub fn open(path: impl AsRef<Path>, template: &str) -> Self;
    pub fn open_in(base: impl AsRef<Path>, relative: &str, template: &str) -> Self;
    pub fn in_memory(value: T) -> Self;
    pub fn path(&self) -> Option<PathBuf>;
    pub fn value(&self) -> T;                 // clone 快照
    pub fn shared(&self) -> Arc<RwLock<T>>;
    pub fn take_notes(&self) -> Vec<String>;
    pub fn reload_if_changed(&self) -> Vec<String>;
    pub fn save(&self, value: T, arrays: &[(&str, &[serde_json::Value])]) -> Result<(), ConfigError>;
}
```

**收益**：两项目各减少约 90~120 行；后续 Pek.RAgent / Pek.RDbProxy / Pek.RPanlServer 的 TOML 热加载也可复用；锁毒化、路径解析、保存顺序只维护一份。

**注意**：`save` 的数组表键由调用方传入（Mail=`"Data"`，Sms=`"Data"`）；`TomlConfig` 仍是底层实现，`TomlConfigStore` 只是“文件 + 共享快照”的薄编排。

**优先级**：**P0**，建议下一轮首先实施。

### 4.2 P0/P1：凭据脱敏（`dhrust::secret::SecretString` 或项目内手写 `Debug`）

**现状**：

- `MailData` 派生 `Debug`（`Pek.RMail/src/settings.rs:59`），包含 `password`；
- `SmsData` 派生 `Debug`（`Pek.RSms/src/settings.rs:23`），包含 `access_secret`；
- `MailSettings`/`SmsSettings` 同样派生 `Debug`，一旦 `{:?}` 打印整份配置即泄露。

**建议**（二选一）：

1. **立即**：两项目手写 `Debug`，把 `password`/`access_secret` 输出为 `***`（改动小、无 API 破坏）；
2. **长期**：`dhrust::secret::SecretString`（`Serialize/Deserialize` transparent，`Debug` 恒为 `***`，`Deref<Target=str>`），供更多项目复用。

**优先级**：安全项 **P0**（手写 Debug）/ **P2**（SecretString 类型化）。

### 4.3 P1：`dhrust::web::form_encode`

**现状重复**：

- `Pek.RSms/src/client/aliyun.rs:157` `form_encode(BTreeMap)`；
- `Pek.RSms/src/client/lianlu.rs:75` 手工拼接数组表单；
- 阿里云 `string_to_sign` 也需要同样的 `k=v&...` 编码。

**建议 API**：

```rust
pub fn form_encode<I, K, V>(pairs: I) -> String
where
    I: IntoIterator<Item = (K, V)>,
    K: AsRef<str>,
    V: AsRef<str>;
```

**收益**：两个客户端共用；`url_encode` 已是 dhrust 能力，天然一致。

**优先级**：P1。

### 4.4 P1：`dhrust::text::{split_phone_numbers, replace_named}`

**现状**：

- `Pek.RSms/src/message.rs:232` 手机号拆分/去重；
- `Pek.RSms/src/message.rs:209` `{%key%}` 占位符替换。

**建议 API**：

```rust
pub fn split_phone_numbers(text: &str) -> Vec<String>;
pub fn replace_named(text: &str, pairs: &[(String, String)], open: &str, close: &str) -> String;
```

**收益**：后续短信/通知/营销项目直接复用；`replace_named` 也可用于邮件模板。

**优先级**：P2（当前单消费方，但语义稳定）。

### 4.5 P1/P2：`dhrust::times::{iso8601_utc, utc_date_of}`

**现状**：

- `Pek.RSms/src/client/aliyun.rs:171` 自行格式化 `%Y-%m-%dT%H:%M:%SZ`；
- `tencent.rs` 用 `now.and_utc().timestamp()` + `now.format("%Y-%m-%d")`，并为此保留直接 `chrono` 依赖。

**建议 API**：

```rust
pub fn iso8601_utc() -> String;                 // 2026-10-25T00:00:00Z
pub fn utc_date_of(unix_secs: i64) -> Option<String>; // 2026-10-25
pub fn utc_now_parts() -> (i64, String);        // (timestamp, date)
```

**收益**：Pek.RSms 可移除直接 `chrono` 依赖；其他对接云 API 的项目复用。

**优先级**：P2。

### 4.6 P2：`dhrust::json::{get_str, get_i64, get_bool}`

**现状**：`Pek.RSms/src/client/mod.rs:94/105` 的 `json_text`/`json_i64` 被阿里云、腾讯云、烽火三家使用；当前返回空串/0，无法区分“缺失”和“空值”。

**建议 API**：

```rust
pub fn get_str(value: &serde_json::Value, key: &str) -> Option<String>;
pub fn get_i64(value: &serde_json::Value, key: &str) -> Option<i64>;
pub fn get_bool(value: &serde_json::Value, key: &str) -> Option<bool>;
```

**收益**：dhrust 已有 `serde_json` 依赖；多个项目解析第三方响应时可复用。

**优先级**：P2。

### 4.7 P2：`dhrust::threading::BlockingQueue<T>`（可选）

**现状**：`Pek.RMail/src/queue.rs:23-100` 是通用“Mutex<VecDeque> + Condvar + 超时/停止谓词”队列；当前只有邮件使用。

**建议 API**：

```rust
pub struct BlockingQueue<T> { /* Mutex<VecDeque<T>> + Condvar */ }
impl<T> BlockingQueue<T> {
    pub fn new() -> Self;
    pub fn enqueue(&self, item: T);
    pub fn try_dequeue(&self) -> Option<T>;
    pub fn dequeue_timeout(&self, timeout: Duration) -> Option<T>;
    pub fn dequeue_timeout_while(&self, timeout: Duration, stop: impl Fn() -> bool) -> Option<T>;
    pub fn count(&self) -> usize;
    pub fn notify_all(&self);
}
```

**收益**：未来任务队列/事件队列可复用；`MailQueueProvider` 变成薄包装。

**优先级**：P2（等第二消费方再下沉也合理）。

### 4.8 P2：`dhrust::io::read_file_limited`

**现状**：`Pek.RMail/src/sender/smtp.rs:179` `attachment.read()` 内部 `std::fs::read` 整文件读入内存；无大小上限。

**建议 API**：

```rust
pub fn read_file_limited(path: impl AsRef<Path>, max_bytes: u64) -> io::Result<Vec<u8>>;
```

**收益**：附件/上传/配置读取统一防线；避免误传超大文件 OOM。

**优先级**：P2。

### 4.9 P3：`dhrust::net::http_client::request_with_retry`

**现状**：`Pek.RSms/src/http.rs:32` 的 `post` 封装了“超时 + 重试 + TLS 选项”，但重试只覆盖传输错误，不覆盖 HTTP 5xx/429。

**建议 API**（可选）：

```rust
pub struct RetryPolicy {
    pub attempts: u32,
    pub delay: Duration,
    pub retry_status: Vec<u16>,
}
pub fn blocking_request_retry(..., policy: &RetryPolicy) -> Result<HttpResponse, HttpClientError>;
```

**注意**：不同项目对 4xx/5xx 的重试策略不同，建议等第二消费方明确需求后再下沉；当前可先在 Pek.RSms 内修正语义。

**优先级**：P3。

### 4.10 P3：`dhrust::errors::AttemptFailure`（可选）

**现状**：

- Mail：`AccountFailure { code, host, error }`；
- SMS：`AccountFailure { code, provider, provider_code, message, raw }`。

**建议**：若统一，定义：

```rust
pub struct AttemptFailure {
    pub target: String,   // Mail=host / SMS=provider
    pub label: String,    // 账号 Code
    pub code: String,
    pub message: String,
    pub raw: String,
}
```

**收益**：诊断格式一致；**风险**：抽象收益有限，Mail 的 `host` 与 SMS 的 `provider` 语义不完全一致，容易过度设计。建议**暂不实施**，仅记录。

### 4.11 P3：`dhrust::threading::spawn_named`

**现状**：`Mailer::send_box_async` 与 `Smser::send_async` 都是 `std::thread::spawn`，线程无名称。

**建议**：`spawn_named(name, f)`（失败时回退 `spawn`），便于排查线程。

**优先级**：P3。

## 8. 不建议下沉/不建议改动清单

- **不**把 `EmailBox`/`MailMessage`/`SmsRequest`/`SmsResult` 放进 dhrust：领域模型，跨领域复用概率低；
- **不**把 SMTP/MIME、阿里云/腾讯云/烽火/连陆签名算法放进 dhrust：协议细节属于业务库；
- **不**为了“统一”强行合并 `MailError`/`SmsError`：错误语义与聚合字段不同，抽象收益低；
- **不**在没有第二消费方前下沉 HTTP 重试与阻塞队列：先修正项目内语义，等通用需求明确；
- **不**使用 `unsafe` 或引入异步运行时来“优化”现有同步 API：当前调用频率低，复杂度不值得。
