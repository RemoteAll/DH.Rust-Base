## 1. 结论摘要

两个库的功能与质量基线健康；本轮没有发现新的 panic/unsafe 风险（生产代码仅 `smtp.rs` 一处固定 MIME `expect`）。性能问题集中在 **SMS 的重复解析/重复克隆/HTTP 每次新建线程与运行时**，以及 **Mail 的 fallback 路径重复快照**。SMTP/短信网络与 TLS 握手仍是绝对大头，库内 CPU 优化只能缩短“发送前准备”和“重试间隔”。

按收益排序：

1. **SMS HTTP：每次尝试新建线程 + 新 tokio 运行时，且无连接复用**。本机 loopback 实测直接调用约 0.28~0.33ms，offthread 包装约 0.46~0.52ms（每次尝试多约 0.2ms）；真实 HTTPS 还有 TCP/TLS 握手。
2. **SMS `SmsData::extend_map` 每次调用重新解析 JSON**：1.4~1.7µs/次；单次发送会调用 6~8 次，合计约 9~15µs。
3. **SMS `split_phone_numbers` 的 O(n²) 去重**：100 个号约 20~30µs，1000 个号约 1.6~1.8ms。
4. **SMS `create_client` / `Smser` 重复克隆配置与账号**：`SmsSettings`（10 账号）克隆约 1.7~2.5µs；`create_client` 约 2~3µs，其中大部分是无用的 settings 克隆。
5. **Mail fallback 路径重复快照**：`SmtpEmailSender::send_with_accounts` 每个账号都会 `settings_snapshot()`（10 账号约 2.5µs/次）；`Mailer::send_box_routed` 也会快照两次。
6. **`reload_if_changed` 每次调用约 49µs**（Mail/SMS 实测，Windows 文件元数据）：适合秒级/文件监听，不适合每封邮件/每条短信轮询。

Mail 的队列与消息构建本身很轻：`MailQueue` enqueue+dequeue 约 161ns，`EmailBox::to_message` 约 0.4µs，`MailMessage::clone` 约 0.43µs。Mail 的主要成本在 SMTP 连接/TLS 握手和附件内存，而不是这些 CPU 小项。

## 3. Pek.RMail 性能分析

### 3.1 已测且可忽略的热点

- `EmailBox::to_message` / `MailMessage::from_box` / `clone` 均 <0.5µs；构造邮件对象不是瓶颈。
- `MailQueueProvider` 入队+出队约 161ns；`Condvar` 入队即唤醒、空闲无周期唤醒，设计正确。
- `MailSettings::socket_option` 约 5ns；`TlsParameters::new` 约 2.3µs，均不是主要成本。
- 小附件 `Attachment::read` 内存克隆约 42ns；真正成本是文件 I/O 与整文件驻留内存。

### 3.3 附件与内存

`AttachmentSource::File` 在 `read()` 时 `std::fs::read` 整文件；`MultiPart` 持有 `Vec<u8>`，发送期间文件内容与 MIME 编码可能同时驻留，峰值约为文件大小的 1.3~2 倍。C# 版同样把 `ContentStream` 复制进 `MemoryBlockStream`，所以这不是 Rust 独有的回归，但 Rust 版缺少大小上限和流式选项，建议至少加 `max_attachment_bytes`。

## 4. Pek.RSms 性能分析

### 4.1 最大 CPU 热点：`ExtendData` 重复解析

`SmsData::extend_map()`（`src/settings.rs:132`）每次调用都 `serde_json::from_str`。各客户端在一次发送中会多次调用：

- 阿里云：`TemplateCode`、`OutId`、`SmsUpExtendCode`、`BaseUrl`、`InsecureTls`/`IgnoreSsl`，约 5~6 次；
- 腾讯云：`SdkAppId`、`TemplateId`、`CountryCode`、`BaseUrl`、`Host`、`Region`、`InsecureTls`/`IgnoreSsl`，约 7~8 次；
- 烽火：`TemplateId`、`BaseUrl`、`InsecureTls`，约 3 次；
- 连陆：`BaseUrl`、`InsecureTls`，约 2 次。

实测单次解析 1.4~1.7µs，`extend_str` 六连调 9~10µs。建议：

1. **每次 `send` 只解析一次**：新增 `SmsData::extend_view()`（持有 `Map`）或 `ExtendView`，提供 `str/bool/i64/base_url/insecure_tls`；客户端在 `send` 开头构造一次。
2. 或给 `SmsData` 加 `OnceLock<Map>` 缓存（`#[serde(skip)]`，自定义 PartialEq/Eq 忽略缓存），但要注意 `Smser` 目前会克隆账号，缓存会随克隆复制，收益取决于是否同时去掉账号克隆。

推荐先做 1（每次发送一次），实现简单、无缓存失效问题。

### 4.2 重复克隆：`Smser` + `create_client`

`Smser::send`（`src/smser.rs:95`）先 `self.settings()` 克隆整份配置，再把已启用账号 `.cloned()` 成 `Vec<SmsData>`；`create_client`（`src/client/mod.rs:40`）又对 `config` 和 `_settings` 各克隆一次，且**四个客户端里有三个根本不用 `SmsSettings`**。实测：

- `SmsSettings::clone`（10 账号）1.7~2.5µs；
- `create_client` 2~3µs，其中大部分是 settings 克隆。

建议：

- `create_client` 对阿里云/腾讯云/连陆只 `config.clone()`，不再克隆 `SmsSettings`；
- 新增 `create_client_owned(config: SmsData, settings: &SmsSettings)` 供 `Smser` 使用：`send` 已经把账号克隆进 `Vec`，`send_accounts` 可直接 `into_iter()` 把 `SmsData` 交给客户端，省掉第二次账号克隆；
- `FengHuoSmsClient` 才需要 settings（代理），且可只保留 `enable_proxy/proxy_url/proxy_token` 三个字段，避免整份 settings 克隆。

预期：每次发送少 2~5µs；账号越多收益越明显。

### 4.3 `split_phone_numbers` 的 O(n²)

`src/message.rs:232` 用 `out.iter().any(|existing| existing == number)` 去重；`SmsRequest::from_numbers` 也用 `mobiles.contains`。实测 100 个号 20~30µs，1000 个号 1.6~1.8ms（约 100 倍增长）。建议：

```rust
pub fn split_phone_numbers(text: &str) -> Vec<String> {
    let mut out = Vec::new();
    let mut seen = std::collections::HashSet::new();
    for part in text.split([',', ';', '|', '，', '；']) {
        let number = part.trim();
        if !number.is_empty() && seen.insert(number) {
            out.push(number.to_string());
        }
    }
    out
}
```

`from_numbers` 同样复用 `seen`。1000 个号预期从 ~1.7ms 降到 ~50µs 量级。

### 4.4 HTTP：线程 + 运行时 + 无连接复用

`src/http.rs:32` 每次尝试调用 `blocking_request_offthread_with`：

- 每次 `std::thread::Builder::spawn` 新线程；
- 线程内 `blocking_request_with` 再新建一个 current_thread tokio 运行时；
- 每次请求 `TcpStream::connect`，没有 keep-alive/连接池（`http_client.rs:708`）。

loopback 实测直接调用 0.28~0.33ms，offthread 0.46~0.52ms；真实 HTTPS 还有 TCP/TLS 握手。建议分两级：

1. **低风险**：dhrust 增加 `blocking_request_auto`——用 `tokio::runtime::Handle::try_current()` 判断：不在 tokio 上下文就直接 `blocking_request_with`，在 tokio 上下文才 offthread。SMS 默认在同步业务线程调用时可直接省掉 0.2ms/次尝试。
2. **中风险**：为短信/HTTP 提供一个持久化阻塞客户端（后台线程持有 tokio 运行时 + 连接池/keep-alive），`Smser` 复用一个实例；可显著降低高频短信的握手成本。此项需要 dhrust `http_client` 支持连接复用，工作量大，建议单独一轮。

另外 `http::post` 每次重试 `body.clone()`，大手机号列表时会有多次分配；可改为 `Arc<[u8]>` 或按引用传入，属于 P3。

| **P3** | `errors::AttemptFailure` | Mail/SMS 的 `AccountFailure` | 统一 `target/label/code/message/raw` | 字段语义有差异，暂不推荐 |

**不建议下沉**：`EmailBox`/`MailMessage`/`SmsRequest`/`SmsResult`、SMTP/MIME、四家短信协议与签名算法——领域/协议细节应留在各自库。

## 7. 建议实施波次

### Wave 2（低风险性能，建议优先）
1. SMS `SmsData` 每次 `send` 只解析一次 `ExtendData`；客户端改用 `ExtendView`。
2. SMS `create_client` 仅烽火克隆 settings；新增 `create_client_owned`，去掉 `Smser` 的二次账号克隆。
3. SMS `split_phone_numbers`/`from_numbers` 改 HashSet + 保序 Vec。
4. Mail `SmtpEmailSender` 覆写 `send_with_accounts`（一次快照）；`send_box_routed` 单次快照。
5. 两项目 `settings_snapshot`/锁毒化恢复改为 `into_inner()` + 告警。
6. `dhrust::web::form_encode` 下沉并替换阿里云/连陆/`post_form`。

### Wave 3（公共能力 + 语义修正）
1. `dhrust::json`、`dhrust::times`、`dhrust::text`、`dhrust::io::read_file_limited`。
2. `dhrust::net::http_client::blocking_request_auto` + `RetryPolicy`；SMS 5xx/429 语义修正。
3. Mail 附件上限、队列上限/背压、`stop_timeout`。
4. `dhrust::secret::SecretString`（可选）。

### Wave 4（较大改造，单独评估）
1. HTTP 持久化阻塞客户端 + 连接池/keep-alive（dhrust）。
2. SMTP 连接复用/连接池（仅高吞吐场景）。
3. `BlockingQueue<T>` 下沉（等第二消费方）。
4. `AttemptFailure`/`spawn_named` 等 P3。
