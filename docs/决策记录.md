## 2026-10-25（二）· 限流引擎审计整改（分片满 O(1) 淘汰）

**背景**：全面审计发现 `FixedWindowStore` 分片满时使用 `retain` + `min_by_key` 全表扫描（O(n)）。
大量唯一键（伪造 IP/头值）填满分片后，每次新键插入都会扫描 8192 项，形成 CPU 热点。

**整改**：分片满时改为 **O(1)** 淘汰任意一个键；`prune_expired()` 保留为显式批量清理。
内存有界优先；被淘汰键计数归零的取舍已写入模块文档。

**验证**：默认特性 **303 passed / 1 ignored**；`cargo clippy --all-targets -- -D warnings` 零告警；
RWaf 侧 55 lib + 2 集成全绿；Linux x64/arm64 musl 交叉检查通过（RWaf）。

## 2026-10-25 · 新增通用固定窗口限流与 IP/MD5 工具（dhrust 0.3.0）

**用户原话**：「帮我参考 G:\Code\Pek.FrameWork\DH.RateLimter 实现 Rust 版本的，而且也要参考其他项目实现全局用户指令相关。同时也要考虑 DH.RustBase 方法提取和复用，先考虑有没有必要把这个限流的项目和 Pek.RWAF 项目中，就不用另外再实现一个单独的限流库了」

**背景**：C# `DH.RateLimter` 的计数存储（Redis `INCR` + 首次创建过期）与 IP/MD5 键压缩是通用能力，不应只在某个 Web 库中实现；HTTP 策略层（七种 `Policy`）合入 `Pek.RWaf::throttle`。

**结论**：
1. 新增 `src/ratelimit.rs`（无 feature、零 HTTP 依赖）：
   - `CounterStore` 抽象（`increment/remove/clear/len`，返回 `CounterHit{count,reset_in}`）——可注入 Redis 共享计数；
   - `WindowLimiter`（`hit(key, limit, window) -> Decision`；`limit==0`/窗口 0 = 关闭且不计数）；
   - `FixedWindowStore`（分片 `Mutex<HashMap>`，按 `sign::fnv1a_64` 分片；每片键数上限 + 过期清理 + 最早键淘汰，防内存无界增长）。
2. 新增 `net::ip_to_num`：对齐 C# `Common.IpToNum`（IPv4/IPv6 大端无符号整数十进制；容忍 `[::1]:80` / `1.2.3.4:80`）。
3. 新增 `sign::md5_short`：对齐 C# `Common.EncryptMD5Short`（完整 MD5 第 8~24 位，16 hex）。
4. **有意不做** C# 的 5 分钟 MD5/IP 内存缓存：Rust 单次计算百纳秒级，避免无界缓存与失效逻辑。

**验证**：`cargo test` **303 passed / 1 ignored**；`cargo clippy --all-targets -- -D warnings` 零告警。
消费方：`pek_rwaf::throttle`（接口级限流）+ `pek_rwaf::ratelimit`（WAF CC 薄封装）；
`Pek.RPanlServer` / `Pek.RAgent` / `Pek.RCard` / `Pek.RDbProxy` / `HLZX.EIP` 均已 `cargo check` 通过。

## 2026-10-23（二）· 旧版 JSON 迁移下沉为 `TomlConfig` 的自动行为（各项目零代码）

**用户原话**：「都是会自动升级调整格式的吧，这种自动的是不是在DH.RustBase中实现就行，要不然还得每个项目都得调整代码」

**结论**：是，已下沉。约定 **同目录同名 `.json` = 旧版配置**（`Config/Foo.toml` ← `Config/Foo.json`）：
- `TomlConfig::load/try_load_with`：TOML 不存在而 `.json` 存在 → 读旧值、**以模板（调用方预设）为基合并**

  旧文件不是合法 JSON 时告警并照常新建；旧文件里模板没有的键给出「已忽略」提示。
- `TomlConfig::save`：保存时顺手把残留的旧 `.json` 备份为 `.json.bak`（避免“新配置生效、旧配置还留着”）。
- 删除了先前暴露的 `config::toml::migrate_json`（以及 Pek.RWaf 的 `migrate_legacy_json`/`merge_json`），
  **只保留一种做法**；HLZX.EIP / Pek.RWaf 的迁移代码同步删除。

**验证**：dhrust `cargo test --features toml --lib config::` **56 项**全绿（新增自动迁移 3 项）；

## 2026-10-20 · `monitor`：CPU 百分比不再恒为 0（短间隔调用不推进基线）

**用户原话**：「Cpu好像没有拿到数据」→「要等一会儿才会有变化。」

**根因**：`update_cpu_percent` 无论是否真正算出结果，都会把采样基线（`LAST_CPU` 的 `at`/`cpu`）
更新为当前时刻。面板一次刷新会连打多个接口（`machine` / `services` / `getProcessList`），
后到的调用把基线顶到 `now` → 差分窗口 `< 200ms` → 全部走「复用上次结果」分支；
一旦上次结果恰好是 0，就**自我复用锁死在 0**，只有碰巧隔得久才有数值
（这正是用户观察到的「要等一会儿才会有变化」）。

**修复**：间隔 `< 200ms` 时复用上次结果，但**基线原样放回、不推进**；
只有真正完成一次 `>= 200ms` 的差分计算才推进基线。任何高频调用方都不再影响下一次有效采样。

**验证**：

- 新增单测 `short_interval_call_does_not_advance_cpu_baseline`（`sys::monitor` 10 passed）；
- 手动基准新增 CPU% 冒烟：连续 10 次高频调用后隔 1.2s 再取，
  实测 `Code 87.98% / WmiPrvSE 61.59% / Code 55.30% / WXWorkWeb 40.22% / dwm 38.96%`，
  并断言「至少一个进程 CPU% > 0」（修复前同场景全 0）。

**口径不变**：CPU% = `Δ(utime+stime) / Δt`，占**单核**百分比，可 > 100；窗口 = 两次有效采样间隔。

## 2026-10-20 · `monitor`：进程 Top 增加监听端口 + 「双榜一次扫描」

**用户原话**（Pek.RAgent 侧）：①「这里是否需要把如果有监听端口号的也给显示出来？」②「RAgent也要考虑性能和资源占用哦，不能自己反而成了资源消耗和消耗的源头了」

**新增 API**（`src/sys/monitor.rs`）：

- `ProcItem.ports: Vec<u16>`（TCP **LISTEN**，升序去重；`ProcItem` 同时补 `#[derive(Clone)]`）；
- `listen_ports_many(&[u32]) -> HashMap<u32, Vec<u16>>`：**只扫传入的 pid**，不遍历全系统
  （Linux：`/proc/net/tcp{,6}` 的 LISTEN 行取 `socket inode → 端口`，再只为这批 pid 读 `/proc/{pid}/fd`；
  Windows：`GetExtendedTcpTable` 一次取全表，IPv4+IPv6，再按 pid 过滤）；2 秒快照缓存；
- `listen_ports_of(pid) -> Vec<u16>`：含**子进程树**（应用常由包装脚本/宿主 fork 出真正监听者），供自动探活复用；
- `top_processes_union(cpu_n, mem_n) -> Vec<ProcItem>`：**一次收集、两次排序、取并集**，
  替代「`top_processes` 调两遍」（面板同时要 CPU 榜与内存榜）。

**内部重构**：`top_processes` / `top_processes_union` 共用 `collect_light()`（轻字段全量）+
`update_cpu_percent()`（差分）+ `finalize()`（仅对榜单补重字段与端口）。

**实测（Windows 本机，约 320 进程，`cargo test --release bench_process_top_with_ports -- --ignored --nocapture`）**：

| 项目 | 单次耗时 |
|---|---|
| `top_processes(20, cpu)` | 41.2 ms |
| `top_processes(20, mem)` | 39.9 ms |
| **`top_processes_union(20, 20)`** | **33.9 ms**（原来两榜合计 ≈ 81 ms → **降约 58%**） |

`listen_ports_many(TOP20)` 那次 41.2 ms 里含一次 `top_processes` 调用（约 40 ms），
即端口扫描本身在 1 ms 量级 —— 不是瓶颈。

**边界**：端口快照以 2 秒为粒度（面板 3 秒刷新），刚 listen 的进程最多滞后 2 秒可见；
权限不足读不到 `/proc/{pid}/fd` 时该进程端口为空（不报错）。

## 2026-10-20 · `panel_auth::TokenStore` 支持会话落盘与滑动续期

**用户原话**（Pek.RAgent 侧）：「RAent的登录是只要重启就要重新输入密码吗?这个能不能做成不要动不动的就被影响到要重新输入密码。因为这个不太可能直接用https的，那么多次输入很容易被截取」

**决策**：面板令牌表从「纯内存 + 固定 24h」升级为**可持久化 + 滑动续期**，但**只做加法、不改既有签名与默认行为**（`Pek.RAgent` / `Pek.RPanlServer` 等调用方无需改动即可继续用旧语义）。

**新增 API**（`src/net/panel_auth.rs`）：

- `ttl_ms()`、`clear()`、`revoke_all_except(keep)`；
- `touch(token) -> bool`：仍有效且剩余不足 `ttl/2` 时把到期时间重置为 `now + ttl`（返回是否改动，供调用方决定是否落盘；避免每个请求都写文件）；
- `snapshot() -> Vec<(token, expire, T)>` / `restore(items) -> usize`：导出未过期项与导入恢复（过期项忽略、容量上限 `MAX_TOKENS = 512`，超出丢最早到期）。

**边界**：库不引入 serde 依赖、不碰磁盘——序列化与文件位置由调用方决定（`Pek.RAgent` 用 `Data/panel-sessions.json`，原子写 + Unix 0600）。

**验证**：`cargo test --features net --lib panel_auth` 10 passed（新增 `token_store_snapshot_restore_and_touch` / `token_store_revoke_all_except`）。
